GitHub OIDC Federation for Azure Trusted Signing (Master Packager)

Scope: GitHub Actions CI/CD only. For local development, see trusted-signing-service-principal-setup.md.

This guide explains the steps to authenticate GitHub Actions to Azure Trusted Signing using OIDC federation (no client secret required).

Goal

Use GitHub Actions to authenticate to Azure without storing AZURE_CLIENT_SECRET, while keeping src/VSTO/WordAddIn/InstallerConfig.json compatible with Azure Trusted Signing.

Current Master Packager Configuration

Your InstallerConfig.json is already configured for OIDC federation:

  • signWith: AzureTrustedSigning
  • credentials: ["WorkloadIdentityCredential"] (required for workload identity auth)
  • endpoint: https://weu.codesigning.azure.net
  • codeSigningAccountName: KutanaBrochet
  • certificateProfileName: KBCodeSigning

No other OIDC-specific configuration is needed.

1) Create (or reuse) an Entra application and service principal

You need an app registration (client ID) that GitHub Actions will use via federation.

Command line

$tenantId = "861f4c18-46fb-469e-84ba-832f4dc43d46"
$subId = "384be71e-d194-46cd-9a6b-d9bd71e91e0a"
$appName = "kb-wordaddins-trustedsigning-oidc"

az login --tenant $tenantId
az account set --subscription $subId

$appId = az ad app create --display-name $appName --query appId -o tsv
az ad sp create --id $appId | Out-Null
$spObjectId = az ad sp show --id $appId --query id -o tsv

GUI alternative

  1. Azure Portal -> Microsoft Entra ID -> App registrations -> New registration.
  2. Create the app (single tenant is typical).
  3. Open the app -> Overview and copy:
    • Application (client) ID
    • Directory (tenant) ID
  4. Go to Enterprise applications, find the app, and note the service principal object ID if needed.

2) Assign Azure Trusted Signing roles

Assign roles at the correct scope.

  • Code signing account scope: /subscriptions/384be71e-d194-46cd-9a6b-d9bd71e91e0a/resourceGroups/Code_Signing/providers/Microsoft.CodeSigning/codeSigningAccounts/KutanaBrochet
  • Certificate profile scope: .../codeSigningAccounts/KutanaBrochet/certificateProfiles/KBCodeSigning

Command line

$accountResourceId = "/subscriptions/384be71e-d194-46cd-9a6b-d9bd71e91e0a/resourceGroups/Code_Signing/providers/Microsoft.CodeSigning/codeSigningAccounts/KutanaBrochet"
$profileScope = "$accountResourceId/certificateProfiles/KBCodeSigning"

az role assignment create --assignee-object-id $spObjectId --assignee-principal-type ServicePrincipal --role "Artifact Signing Certificate Profile Signer" --scope "$profileScope" --subscription $subId
az role assignment create --assignee-object-id $spObjectId --assignee-principal-type ServicePrincipal --role "Artifact Signing Identity Verifier" --scope "$accountResourceId" --subscription $subId

GUI alternative

  1. Azure Portal -> Code Signing Accounts -> KutanaBrochet.
  2. Open Certificate profiles -> KBCodeSigning -> Access control (IAM).
  3. Add role assignment: Artifact Signing Certificate Profile Signer.
  4. Go back to the account-level Access control (IAM) and add: Artifact Signing Identity Verifier.

3) Add a federated credential for GitHub

This is the OIDC trust between GitHub and Entra.

Command line

# Example: trust only main branch
$subject='repo:kutana-brochet/office-addins:ref:refs/heads/main'; $body=[ordered]@{name='github-main';issuer='https://token.actions.githubusercontent.com';subject=$subject;audiences=@('api://AzureADTokenExchange')}; $json=$body | ConvertTo-Json -Depth 3 -Compress
Set-Content -Path .\fedcred.json -Value $json -Encoding utf8
az ad app federated-credential create --id $appId --parameters "@fedcred.json"

If your default branch is master, use: $subject='repo:kutana-brochet/office-addins:ref:refs/heads/master'

GUI alternative

  1. Azure Portal -> Entra ID -> App registrations -> your app.
  2. Open Certificates & secrets -> Federated credentials -> Add credential.
  3. Choose GitHub Actions deploying Azure resources.
  4. Set:
    • Organization: kutana-brochet
    • Repository: office-addins
    • Entity type: Branch (or Environment)
    • Branch: main or master
  5. Audience: api://AzureADTokenExchange.

4) Configure GitHub repository settings

Store non-secret IDs in Variables or Secrets; no client secret is needed for OIDC.

  • AZURE_CLIENT_ID (app/client ID)
  • AZURE_TENANT_ID
  • AZURE_SUBSCRIPTION_ID

GUI

GitHub -> repository -> Settings -> Secrets and variables -> Actions.

  • Add as Repository variables (or Environment variables if using protected environments).
  • If your policy requires it, you can store them as secrets.

5) Update GitHub Actions workflow

Use OIDC login, then run your existing MSI task.

What to change in your workflow

  1. Add this at workflow level so GitHub can mint an OIDC token for the job:
    • permissions.id-token: write
  2. Keep contents: read so checkout can read repository contents.
  3. Create a GitHub OIDC token file and export AZURE_FEDERATED_TOKEN_FILE before signing/build steps.
  4. Pass client/tenant/subscription IDs from repository variables.
  5. Keep AZURE_TOKEN_CREDENTIALS=prod so Azure SDK auth uses production credentials in CI.
name: Build Signed MSI

on:
  workflow_dispatch:
  push:
    branches: [ main ]

permissions:
  id-token: write
  contents: read

jobs:
  build-msi:
    runs-on: self-hosted
    env:
      AZURE_CLIENT_ID: ${{ vars.AZURE_CLIENT_ID }}
      AZURE_TENANT_ID: ${{ vars.AZURE_TENANT_ID }}
      AZURE_SUBSCRIPTION_ID: ${{ vars.AZURE_SUBSCRIPTION_ID }}
      AZURE_TOKEN_CREDENTIALS: prod
    steps:
      - uses: actions/checkout@v4

      - name: Create Azure federated token file
        shell: pwsh
        run: |
          $audience = [Uri]::EscapeDataString('api://AzureADTokenExchange')
          $tokenRequestUri = "$env:ACTIONS_ID_TOKEN_REQUEST_URL&audience=$audience"
          $tokenResponse = Invoke-RestMethod `
            -Headers @{ Authorization = "bearer $env:ACTIONS_ID_TOKEN_REQUEST_TOKEN" } `
            -Uri $tokenRequestUri

          $tokenPath = Join-Path $env:RUNNER_TEMP 'github-oidc-token.jwt'
          Set-Content -Path $tokenPath -Value $tokenResponse.value -NoNewline
          "AZURE_FEDERATED_TOKEN_FILE=$tokenPath" >> $env:GITHUB_ENV

      - name: Install Task
        uses: arduino/setup-task@v2

      - name: Build signed MSI
        shell: pwsh
        run: task msi:word

How this works at runtime

  1. GitHub issues a short-lived OIDC token for the job (id-token: write).
  2. The workflow writes that token to AZURE_FEDERATED_TOKEN_FILE.
  3. Master Packager reads that token through Azure.Identity WorkloadIdentityCredential.
  4. The MSI build signs through Azure Trusted Signing without AZURE_CLIENT_SECRET.

Notes:

  • Ensure mpdev is available on the runner. If not, use a self-hosted Windows runner with Master Packager preinstalled.
  • Keep AZURE_TOKEN_CREDENTIALS=prod in CI to prefer workload/environment credentials.
  • If your default branch is master, update both the workflow trigger branch and the federated credential subject to master.

6) Integrate with InstallerConfig.json

Master Packager defaults Azure Trusted Signing to EnvironmentCredential, so OIDC builds must explicitly select WorkloadIdentityCredential.

Recommended checks:

  1. Keep Trusted Signing fields as currently configured.
  2. Include the workload identity credential selector:
"digitalSignature": {
  "signWith": "AzureTrustedSigning",
  "credentials": [
    "WorkloadIdentityCredential"
  ]
}
  1. Keep account/profile names exact (KutanaBrochet, KBCodeSigning).
  2. Ensure signing exclusions remain intentional:
    • Current exclusion signs only files matching KutanaBrochet*.dll and excludes other DLLs.
  3. Prefer HTTPS timestamp endpoint if supported by your process:
    • https://timestamp.acs.microsoft.com

7) Validation checklist

  1. Azure role assignments are visible for the service principal.
  2. Federated credential subject matches your workflow branch/environment.
  3. Workflow has permissions: id-token: write.
  4. The workflow creates AZURE_FEDERATED_TOKEN_FILE.
  5. task msi:word produces signed output in Installers/.

Troubleshooting

  • DefaultAzureCredential failed to retrieve a token

    • Confirm AZURE_FEDERATED_TOKEN_FILE is created before signing.
    • Confirm $.digitalSignature.credentials contains WorkloadIdentityCredential.
    • Confirm AZURE_TOKEN_CREDENTIALS=prod in CI.
    • Confirm no stale AZURE_CLIENT_SECRET from runner machine scope if moving to OIDC-only.

  • 403 Forbidden

    • Role assignment missing at account/profile scope.
    • Role propagation delay; retry after a few minutes.

  • MissingSubscription

    • Invalid or truncated scope path; must begin with /subscriptions/....

  • Signing runs locally but fails in Actions

    • Federated credential subject mismatch (branch/environment/repo mismatch).
    • mpdev not installed on runner.
